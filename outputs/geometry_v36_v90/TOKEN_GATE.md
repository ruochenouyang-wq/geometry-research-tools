# Token 阶段验收口径（在批量实测前固定）

用户要求优先优化 token，达到足够水准后继续收紧不等式，直到 V90。这里的“足够”限定为当前结构化数学工具的接口工程判断，不是模型推理 token 已最优，也不代替实际模型任务评测。

计量采用 tiktoken 0.11.0 的 o200k_base 与 cl100k_base。两套都是真实文本编码器；不声称任一就是 GPT-5.6/Astra 的实际编码映射。保留输入、输出、首次使用说明及后续查询的累计文本计数；未知 API 包装和隐藏推理不估算。官方另提供[模型输入 token 计数接口](https://developers.openai.com/api/reference/python/resources/responses/subresources/input_tokens)，本轮没有调用它或付费模型。

工程关口：

1. 所有已支持状态保留任务绑定、目标、几何/函数空间或 ansatz 范围、方向正确的上下界、可取回证据及核验强度。有效的旧证书不因压缩改变原题结果；篡改、错题诊断和错类型引用被拒绝。
2. 两套编码器下，默认决策回执的中位数不超过 250 个文本 token、90 分位不超过 500；明确说明这些是展示层数据。
3. 原题请求加决策回执的中位数不超过 600 个文本 token；首次协议说明和完整证书取回另外计入会话表，不能藏在预计算之外。
4. 同时展示完整结果读取、旧 CLI 原始简报、包含必需信息的精简基线。旧 CLI 如果更短照实报告，不把信息不足的简报伪装成同任务结果，也不宣称引用方案在读完整证明的任务上仍有同样节省。
5. 验证会话恢复、失败结果、引用失效和按需取回。强制预算不足时报告无法容纳，不能靠删去作用域或把 unresolved 改为 proved 达标。

满足以上关口后，允许将主要开发资源转向数学精度。该判断基于足够小的接口负担与通过的工程测试，不宣称已找到最短可能编码或已经验证模型理解率。后续仍应保留所有压缩负收益和额外取回开销。
