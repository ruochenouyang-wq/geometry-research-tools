# 延迟启动的独立分析与审查

结论：`evaluate_task` 可以安全地推迟 `EvidenceStore` 与 `RequestRunner` 的构造，因为它的调用路径不读取两者，也不通过它们执行数学检查。当前实现保留了全部原题、空间、精度与证据检查，把交互组件的首次初始化纳入首次 `handle` 的实测预算，并保留必要的目录检查。私有奇异数学模块也可等到实际求解或验证奇异证书时初始化。

本次新增的独立功能测试 **15/15 通过**。检查中发现一次首次交互初始化失败会丢失已有形状缓存，主实现已修复，回归通过。下述结论对应明确源码哈希，不是新留出的性能结论，也不是全面并发或形式化数学认证。

## 冷启动开销的定位

使用同机 Python 3.12 与 `-B`，在 7 轮新进程中交替测量冻结 v317 和冻结首版 release。构造函数使用临时存储目录；没有提前执行任务。没有使用分析器的计时中，仅在版本计算和私有模块加载边界记录进程 CPU；这会增加很小的观察开销。标准库测试准备在计时外，公共模块导入与服务构造分别计时。机器未隔离，表中是这一轮的描述性中位数。

| 阶段 | v317 CPU 毫秒 | 首版 release CPU 毫秒 |
|---|---:|---:|
| 服务模块导入 | 54.655 | 56.052 |
| 服务构造 | 5.943 | 13.967 |
| 构造内版本计算次数 | 2 | 3 |
| 构造内全部版本计算 | 1.180 | 0.808 |

首版 release 五个私有模块加载的 CPU 中位数为：`direct` 1.335 毫秒、`fast_math` 2.813 毫秒、`adaptive_singular` 2.469 毫秒、`verification` 0.425 毫秒、`research_service` 1.094 毫秒。构造额外开销主要来自始终执行的私有模块编译和加载，而不是反复计算版本。另一次单独的 `cProfile` 构造剖析也显示源码编译占主要部分；分析器结果仅用于定位，不作为提速数据。

减少重复版本计算仍然合理，但这里只有约 0.4–0.5 毫秒的直接空间，不能把它说成主要收益。按服务实例计算一次，然后让请求内缓存、证据存储验证版本和请求缓存命名空间共用该值即可。跨实例永久缓存版本会错过代码变更，不建议采用。

延迟加载的费用不能隐藏。如果后续请求确实使用奇异求解或奇异证书，私有数学模块仍须构造，并计入该次真实使用。当前普通谱请求先使用共享的冻结加速生成模块，省去尚未使用的私有奇异流程；初始化后再走私有数学模块。因此冷启动和后续调用成本都应单独报告，不能仅展示延迟后的构造时间。

## 为什么推迟交互组件是合理的

冻结调用链为 `evaluate_task → _research → _total_budget`。谱分支使用求解器与绑定验证器；函数逼近分支另外使用 `shape_cache`。这个路径不使用 `store`、`runner`、证据写入、请求去重或交互使用量台账。旧构造器却立即导入并创建所有这些组件。

在临时进程中，审查者用原私有服务类构造了没有 `store`、没有 `runner`，只有形状缓存及原求解绑定的数学适配对象。D05、D06、原题函数逼近与原题谱四个公开开发任务均成功，完整证书与完整构造服务逐字相同，返回字段集合相同（外层重放诊断字段除外），结果通过旧验证器的原题、空间与精度绑定检查。这是架构可行性检查，没有拿该内存实验声称实际提速。

当前产品实现使用 `DemandService` 延迟构造，而不是依赖这个临时实验对象。构造时仍检查并创建规范化存储目录；第一次 `handle` 前再次检查目录是否被替换为符号链接、规范位置是否改变，然后调用原服务构造器。原 `EvidenceStore` 的路径与版本检查、原 `RequestRunner` 的输入、缓存和台账逻辑都保留。初次 `handle` 后，摘要、证据读取和错误原题绑定检查继续执行原行为。

`shape_cache` 是数学适配器的真实状态，必须跨数学调用和首次交互调用保留。检查曾证明：先执行逼近，再让首次 `RequestRunner` 初始化抛出异常，原实现会重置并丢失已有缓存。当前用 `try/finally` 恢复原缓存，初始化成功标志只在全部组件完成后设置；失败后仍能重试，且不丢失之前的规划状态。

返回的精确证书保持相同。版本命名空间、计时、是否创建组件以及实际缓存命中计数会如实反映新执行流程，不应要求这些诊断值与首版 release 逐字相同。

## 对延迟私有数学模块的审查

私有 `verification` 和 `research_service` 保持轻量初始化，普通证书格式判断不会无意中构造完整私有数学流程。首次奇异求解及首次 `adaptive_singular_temple_v1` 证书验证都会执行 `_ensure_math`。模块构造由 `RLock` 保护，在 `direct`、`fast_math`、`adaptive_singular` 全部建立后才发布成功状态。

独立测试在第二个私有模块加载时制造失败，确认失败后不发布模块属性、成功标志仍为假，下一次初始化可以完成并验证原题证书。四个线程同时首次初始化，只构造一套私有模块。测试也覆盖普通谱→奇异谱→普通谱，以及奇异谱→普通谱→奇异谱，两种顺序中的每份完整证书都与旧 v317 逐字相同，且通过旧绑定验证。

这保留了先前请求内缓存设计的所有权与版本原则。延迟初始化不构成跳过验证的理由，不能根据求解器的成功标志、目标已达成或已有 source 名称直接接受证书。

## 新增独立检查

测试文件为 [test_startup_independent.py](test_startup_independent.py)，15 个测试方法覆盖：

- 构造时没有私有数学模块、形状缓存、证据存储与交互执行器对象。
- 纯 `evaluate_task` 在禁止构造存储与执行器的条件下仍完成原验证，错误数学界仍被拒绝。
- 首次 `handle` 保留此前形状缓存；初始化失败后缓存仍在，后续调用可重试。
- 版本只计算一次，数学运行时、存储验证与请求缓存使用同一个版本。
- 假时钟明确验证首次交互初始化收费：人为加入 0.25 秒初始化成本后，0.1 秒预算被判超出；同一证书仍有效、达到数学目标，第二次调用不重复收费。没有依赖真实机器速度的阈值断言。
- 首次奇异证书验证按需构造数学模块；数学初始化失败不发布半成品，重试成功。
- 构造时拒绝根符号链接与普通文件；首次使用前根目录或父目录被替换时拒绝重定向，恢复原目录后可成功使用。
- 四线程首次数学初始化和四线程首次交互初始化都只创建一套所需组件。
- 两种简单/奇异调用顺序保持精确证书与原题绑定；延后发生的摘要、证据读取和错误空间绑定行为正常。

这些是功能检查，不是并发性能测量。原 `RequestRunner` 自身说明它是顺序执行器；本次“首次交互只初始化一次”的检查不应被扩大解释为对整个交互执行器任意并发访问的全面保证。
