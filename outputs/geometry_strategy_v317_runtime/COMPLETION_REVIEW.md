## 4. 效率、API 与可见 token 不能混用

性能实验实际调用 **`ResearchService.evaluate_task`**，返回完整数学结果并由冻结验证器另外重放。它不使用证据存储、交互请求去重、摘要写入、`fetch` 或交互账本。当前按需初始化因此具有合理的真实收益；但“完整冷 session”应完整表述为**完整评测适配器进程**，不能自动改写为“默认交互服务从摘要到取证都同比变快”。

`handle` 与命令行入口仍可运行，首次 `handle` 会真正构造证据存储和交互执行器，并计入该次调用的总预算。相应功能、失败重试及原题绑定有 54 项检查中的覆盖；完整交互链路的对照性能没有被这次评测测量。`usage` 台账的生命周期、嵌套阶段计时和进程总成本也不同，不能直接相加。

可见文本进步属于原 v317 **可选的 `interaction.choose_response` 组件**。默认 `handle` 调用 `present_result` 并追加 `usage`/`interaction`，没有调用 `choose_response`。因此 **2.85%/3.47% 不能写成默认整个服务已节省的 token**，也不是实际模型费用下降。

[重新计数记录](metrics/TOKEN_RECOUNT.json)核对原脚本四种场景均与原结果一致：单次 308/305 对 308/305；12 次无补读 5922/5878 对 5753/5674；每次补读时 66490/65666 对 66321/65462。收益依赖既定交互和原请求可恢复语义，单次为零、补读会稀释收益。编码器是公开离线词表，没有与实际当前模型用量建立对应。重新计数的父进程 CPU 还排除了编码子进程，不能误称编码实验完整 CPU。

这个可调用组件已经是实际交付的功能，原 goal 没有要求它必须接入默认请求路径；不能为了完成状态临时虚称已集成，也不必新增原先没有要求的默认行为。其入口及限制已在 [TOOL_GUIDE.md](TOOL_GUIDE.md)说明。

## 6. 成本与长期目标仍须正确交付

完整历史研发 token、逐 agent 重试、人工、维护、所有资源费用无法从现有公开工件完整重建。当前 goal 要求记录成本；指导报告同时要求取不到的数值记未知。因此最终报告应列清**已经取得的准备、运行、失败、验证等数据，以及仍未知的部分**，而非声称完整实测账单已齐。

成稿[成本账本](metrics/COST_LEDGER.json)汇总两个验收修订的九次完整比较、245 个比较进程及两次配置选择。本次按九份原始报告的逐进程费用独立重新加总，得到相同的墙钟 **168.590795 s**、CPU **167.736120 s**；两次准备各计一次。这是列明实验的成本，不含全部研发、测试、分析、模型和人工。账本及主报告均明确这个限制。

[goal 用量快照](metrics/GOAL_USAGE_SNAPSHOT.json)保存平台返回的 `tokensUsed=4,572,178`、`timeUsedSeconds=31,354`；主报告按总体平台计数表述，没有把它写成逐模型账单、全部实际计费 token、金额或数学计算耗时。父进程 CPU、子进程 CPU、墙钟、累计运行和离线文本计数仍须按各自口径理解。评测程序不调用外部模型，只说明那些程序的调用数为零，不能将参与研发的主任务和 agent 成本写成零。

本轮未执行真实跨模型对照，也没有测试模型理解率和实际输入/输出/隐藏推理用量。按当前 goal 的原文，这些是必须诚实披露的未测项及长期研究任务，不是本轮已安排而漏做的模型实验。**长期目标仍未完成**：没有证据证明较低成本模型胜过较强模型或半小时胜过八小时，不能由本地工具资源门槛推得。
